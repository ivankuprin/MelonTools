# Security model

This document describes what Melon Tools protects, what it does not protect,
and where trust is anchored. It covers the 2.3.1 macOS and Windows builds.

## Design summary

- **Local first.** The app has no Melon Tools backend, no telemetry endpoint,
  and no maintainer-operated relay. Account credentials and provider keys stay
  on the device.
- **Loopback services.** The OpenAI-compatible gateway and the Codex DevTools
  bridge listen on `127.0.0.1` only.
- **Direct provider calls.** Requests go to the providers the user configures
  (OpenAI/Codex, Anthropic, Google, OpenRouter, OpenCode) and to GitHub for
  updates.
- **Verified updates.** The updater accepts HTTPS GitHub hosts only and checks
  the downloaded file's SHA-256 before installing it.
- **Signing is not yet available.** The 2.3.1 builds are ad-hoc signed (macOS) and the Windows exe/installer are unsigned. This is a distribution-integrity gap, not a runtime
  vulnerability; see [Signing and notarization](#signing-and-notarization).

## Data at rest

### macOS

| Path | Contents | Protection |
|------|----------|------------|
| `~/Library/Application Support/MelonTools/codex/accounts.json` | Account records, OAuth tokens | Atomic write with mode `0600`; not encrypted at rest |
| `~/Library/Application Support/MelonTools/gateway/api-key` | Gateway bearer key | `0600` |
| `~/Library/Application Support/MelonTools/gateway/management-secret` | Sidecar management secret | `0600` |
| `~/Library/Application Support/MelonTools/gateway/config.yaml` | Gateway config, provider keys, access key | `0600` |
| `~/Library/Application Support/MelonTools/model-sources.json` | Provider selection and settings | App support directory |
| `~/.codex/auth.json`, `~/.codex/config.toml` | Codex login and routing | Config written atomically with `0600`; backup `config.toml.melon-backup` is `0600` |
| `~/Library/Logs/MelonTools/` | Updater and diagnostic logs | `0600` |

The vault and gateway configuration are protected by POSIX permissions, not by
encryption. Anyone who can read the user's files (root, a backup, a sync tool)
can read the tokens. **Enable FileVault and protect backups.**

### Windows

| Path | Contents | Protection |
|------|----------|------------|
| `%APPDATA%\MelonTools\codex\accounts.json` | Account records, OAuth tokens | Token fields (`id_token`, `access_token`, `refresh_token`) are DPAPI-protected as `dpapi2:<base64>` with application entropy under the current user. Legacy `dpapi:` (v1) and plaintext values are migrated on the next save; plaintext that looks like a tag is stored as `plain:<base64>` |
| `%APPDATA%\MelonTools\settings.json` | API keys, management secret, settings | Secret fields DPAPI-protected (`dpapi2:` prefix) under the current user; legacy `dpapi:`/plaintext is migrated on the next save |
| `%APPDATA%\MelonTools\gateway\config.yaml` | Gateway config, provider keys, access key | Plaintext required by the engine; protected by the user-profile ACL, not DPAPI |
| `%APPDATA%\MelonTools\gateway\auths\*.json` | Account auth files used by the engine | User-profile ACL |
| `%APPDATA%\MelonTools\gateway\gateway.log` | Gateway log | User-profile ACL |
| `%USERPROFILE%\.codex\auth.json`, `config.toml` | Codex login and routing | Windows user-profile ACL; backup `config.toml.melon-backup` |

DPAPI protects data at rest against another user account and against offline
copies of the file on a different machine. It does **not** protect against
malware running as the same user, which can call DPAPI with the same key.
Windows Home editions should use BitLocker or device encryption.

The vault JSON shape is portable between macOS and Windows by design, but
Windows token values are DPAPI-bound to the current user and machine. Copying
`accounts.json` to another machine does not expose the tokens, but those
accounts cannot decrypt and must be re-added (the app marks them
`needsRelogin`). Treat the file as a secret.

## Local gateway

- Binds to `127.0.0.1` on port `18317` by default (configurable in Settings).
- Requires a bearer access key generated by the app. The key is stored locally
  and written into the gateway configuration.
- Remote management is disabled (`allow-remote: false`); the engine control
  panel and auto-update panel are disabled.
- The engine's management secret is local and used only by the app.
- Loopback traffic is plain HTTP. It does not leave the machine, but any local
  process that obtains the access key can call the gateway. That is equivalent
  to the process reading the user's local files; it is outside the isolation
  boundary.

Codex is pointed at the gateway by rewriting the Codex configuration. The
original file is backed up, and the rewritten file carries the bearer token, so
both are written with restrictive permissions (`0600` on macOS, user-profile
ACL on Windows).

## OAuth loopback

Browser logins use OAuth with PKCE. The app starts a one-shot loopback HTTP
server on `127.0.0.1` (ports 1455 and 1457 for the Codex flow) to receive the
authorization redirect. The server is short-lived and only accepts the local
redirect. Tokens are then written to the local vault.

## Composer chips and CDP

The chips bridge connects to the Codex desktop app through the Chrome DevTools
Protocol:

- The app launches or restarts Codex with
  `--remote-debugging-address=127.0.0.1` and an ephemeral debug port.
- It enumerates DevTools targets over `http://127.0.0.1:<port>/json` and
  injects the chips script into the matching renderer.
- The debug port has **no authentication**. Any local process that can reach
  the port can inspect or drive the Codex renderer while the bridge is active.
- The port is bound to loopback and is short-lived, but loopback is not a
  security boundary between processes running as the same user.

Do not run untrusted local software while the chips bridge is active. Do not
expose the debug port through a proxy, tunnel, or remote debugging address.
Closing Codex or disabling the bridge removes the listener.

## Updater trust

The updater fetches release metadata from
`https://api.github.com/repos/ivankuprin/MelonTools/releases/latest` and assets
from HTTPS GitHub hosts only:

- `api.github.com`
- `github.com`
- `release-assets.githubusercontent.com`

Redirects are re-checked against the same allowlist. The downloaded artifact
must match the release asset digest or the first 64-character hex token of the
asset's `.sha256` sibling. A mismatch aborts the install.

On macOS the app must run from `/Applications`; it quits, swaps the bundle, and
relaunches. On Windows the updater applies only the release it checked and
replaces the single executable after exit.

**The updater verifies integrity, not publisher identity.** Until signing is
enabled, trust is anchored in GitHub TLS, the repository account, and the
published SHA-256. A compromised GitHub account or release could publish a
matching malicious artifact. When code signing is configured, Gatekeeper and
SmartScreen add an OS-level publisher check at launch, but the updater itself
still relies on the checksum.

## Signing and notarization

Current state: **BLOCKED on certificates.**

- macOS: ad-hoc signature only. Gatekeeper may require right-click → Open.
- Windows: no Authenticode signature. SmartScreen may warn.

The release workflow has conditional signing steps and `packaging/` contains
the scripts and the required-secret list. Missing secrets produce unsigned
artifacts and an annotation in the release notes; the release job does not fail.
See [packaging/README.md](../packaging/README.md).

## Trust boundaries

| Boundary | In scope | Out of scope |
|----------|----------|--------------|
| Network | Loopback-only listeners; HTTPS to providers and GitHub | A malicious local process, a compromised provider, or a compromised GitHub account |
| Local users | File permissions and DPAPI isolate other OS users | Root/Administrator, same-user malware, debuggers, screen capture |
| Storage | Atomic writes, restrictive permissions, DPAPI on Windows | Full-disk encryption, backups, cloud sync, physical access |
| Updates | HTTPS allowlist and SHA-256 integrity | Publisher authenticity until signing is enabled |
| CDP | Loopback-only, ephemeral port | Any local process that connects to the debug port |

Melon Tools is a single-user desktop tool. It does not attempt to isolate
providers from each other, sandbox the gateway engine, or protect a machine
that is already compromised.

## Reporting

Report suspected vulnerabilities through
[GitHub private vulnerability reporting](https://github.com/ivankuprin/MelonTools/security/advisories/new).
Do not post credentials, tokens, or exploitable details in a public issue.
